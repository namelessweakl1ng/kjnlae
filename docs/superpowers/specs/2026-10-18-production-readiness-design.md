# kjnlae production-readiness design — review draft

**Status:** proposed gates, frozen before any *new* model training or final evaluation. This document does not promote the existing model or authorize publication. The baseline is the unpublished v0.3 candidate at commit `14e7f47`; its 120-case authored test had 9/80 benign false alarms and 40/40 attacks detected, while the old 30-case regression had 6/12 benign false alarms and 2/18 missed attacks. These opened sets remain historical diagnostics.

## Intended outcome and decision

kjnlae should remain a free, local, English-first Python dependency for bounded text screening and independent host-side action and output controls. The next release path is **evidence-led, integration-specific beta**, then a separate production review. Shipping the current candidate as broadly production-ready would misstate its false-positive risk; demanding universal prompt-injection prevention would be untestable. A limited beta gives consenting developers a measured operating point and rollback while new independent evaluation and security evidence accumulate.

`Guard.scan` is only an injection classifier. It does not grant a principal, tenant, resource, destination, approval, or tool permission. `ActionGateway`, `GuardedExecutor`, and `OutputGuard` remain the enforcement boundary. An application that invokes tools outside these controls is outside the claimed protection. The detector remains model-only, with no regex or untrained fallback; supported content is either completely inspected or explicitly `INCOMPLETE`/rejected. Scanning must run offline after explicit verified installation.

Supported scope is English text from direct users, RAG/retrieved passages, webpages, email and attachments represented as text, tool responses, and agent proposals, within the current 32,768-codepoint limit and documented view/window budgets. Excluded claims include arbitrary multilingual detection, OCR or binary attachments, arbitrary secret discovery, compromised host credentials/policy, universal LLM resistance, and high-impact healthcare/HR suitability without an application-specific external review. A static API key authenticates one service deployment; downstream apps must supply verified per-user identity and transactional resource checks.

## Evidence design

Before another model or threshold is selected, freeze a **new** independent final set with reviewed labels, stable source/family IDs, licenses and hashes. Use separate diagnostic/development data for failure analysis, training, validation, calibration and threshold selection. Check exact, normalized and near-duplicate overlap by family and text. The opened 30/50/120 fixtures and Deepset TEST are historical comparisons only. If an external benchmark's licensing, setup or labels do not match this threat model, report that mismatch instead of relabeling it silently. BIPIA classifier cases and AgentDojo end-to-end tasks are separate reports; neither substitutes for the other.

The proposed minimum final evidence for a *production-candidate review* is **1,000 benign and 500 attack examples**, sampled across supported sources with at least 100 benign and 50 attack examples per claimed source. Count independent content families, not source variants, toward these minima. Include hard benign quotations, code, documentation, ordinary authorized workflows, long/markup/Unicode content, and tail-position attacks. Preserve all failures and publish confusion matrices, source/category breakdowns, latency distributions and 95% Wilson intervals; report correlated families separately. These numbers are evaluation minimums, not guarantees of real-world representativeness. Final cases are opened once per preselected candidate/threshold; later tuning requires a fresh final set.

## Predeclared review gates

The values below are **proposed application-risk budgets**, not measurements of the present candidate. Revisit them only before opening new final data, with a dated rationale; never relax them after seeing final outcomes.

| Property | Limited beta gate | Production-candidate review gate |
|---|---|---|
| Benign false positives | At most 5% overall on at least 400 independent benign families; no claimed source above 10%. | At most 2% overall and 95% Wilson upper bound at most 3.5% on at least 1,000 benign families; no claimed source above 5%. |
| Active attack recall | At least 95% point estimate and 95% Wilson lower bound at least 90% on at least 200 independent attacks. | At least 98% point estimate and 95% Wilson lower bound at least 95% on at least 500 independent attacks; per-source recall at least 90%. |
| Legitimate agent work | At least 95% authorized completion in at least 200 fictional tasks; explain each rejection. | At least 98% authorized completion and at most 2% benign task rejection in at least 300 representative tasks. |
| Unauthorized effects | Zero observed unauthorized callbacks/releases in all policy-invariant tests and at least 150 diverse agent attempts. | Zero observed unauthorized effects in at least 300 attempts, including detector misses; for zero of 300, the one-sided 95% upper bound is about 1%. This does not prove zero real-world risk. |
| Coverage and failure | 100% of supported inputs either fully mapped/inspected or explicitly incomplete/rejected; no sensitive action executes when its required control fails. | Same, including injected corrupt/missing/time-out/partial-window failures, concurrent/repeated calls and rollback. |
| CPU runtime | Measure p50/p95 and memory on 4 vCPU/8 GiB reference host; no hard beta claim before workload measurement. | For warm scans: p95 at most 250 ms for up to 2,000 codepoints and at most 2 s at the supported input bound, peak resident memory at most 1.5 GiB. Record throughput and hardware; revise *before* final testing if the reference host is unsuitable. |
| Distribution and platform | Clean Linux wheel install, offline real-weight CLI/SDK/API and Docker smoke; missing platforms labeled unverified. | Clean installation and no-weight CI for all advertised Python/OS combinations; real-weight Windows, macOS and Linux checks on at least one supported Python version each, with untested combinations explicitly labeled. |

A passing authored fixture alone is insufficient. Any material safety regression, unresolved high/critical runtime dependency advisory, integrity mismatch, incomplete inspection falsely reported as complete, unauthorized effect, or missing independent authorization boundary blocks production promotion regardless of aggregate scores. Domain-specific high-impact use additionally needs an external security review/red team and the host's own risk acceptance. The pilot measures real integration false alarms, misses reported by consenting users, incomplete scans, latency, support burden and rollback; it stores no full prompt by default.

## Versioning and promotion boundary

Preserve the public v0.2 model and its installer as rollback. A new model gets a separate versioned Hugging Face repository, genuine safetensors/tokenizer/config/model card, integrity manifest, selected threshold, and a distinct filled ONNX hash. The original and derived artifacts must agree on labels, threshold, provenance and per-window decisions/offsets. Record the immutable Hugging Face commit SHA after publication, then download it afresh into a clean location, verify every file/hash, and run offline install/CLI/SDK/API checks. Only **after explicit owner release approval** may the installer default and Python package version change. Model version and package version remain separate. A candidate that fails a gate stays experimental and is neither published nor promoted as a production model.

## Beta and rollback

A limited beta begins only with developer consent and an integration guide that enforces every sensitive action outside the classifier. Use fictional or appropriately handled data, metadata-only diagnostics, a documented support channel, and an owner able to revert the model pin without overwriting existing installations. Record version, immutable model identity, threshold, host type, observed incomplete rate, latency and false-alarm appeals. Stop or roll back on any unauthorized effect, hash failure, systematic source-specific false blocks, or sustained incomplete scans. A separate signed-off production review evaluates these observations and any external assessment; no generic production-ready badge follows automatically from beta completion.
